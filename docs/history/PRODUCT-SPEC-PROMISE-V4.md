## 1. 제품 결정

`올여름 내가 토스할게`는 두 개의 여름 장면과 가능한 날짜를 한
사람에게 건네고, 상대가 하나를 선택해 자신의 역할을 보태면 실제
약속이 확정되는 1:1 비게임 미니앱이다.

비치발리볼은 경기 규칙이 아니라 `선택권과 작은 약속을 먼저 건네는
행동`의 시각적 은유다. 재미는 점수나 반응속도가 아니라 `상대가 둘
중 무엇을 고를지 기다리는 기대`와 `답장이 실제 약속으로 바뀌는
순간`에서 만든다.

### 한 줄 소개

> 두 개의 여름을 토스하면, 친구가 하나를 받아 우리 약속을 완성해요.

### 사용자 약속

> 오픈 채팅으로 날짜와 할 일을 길게 조율하지 않고, 60초 안에
> 부담 없는 두 가지 제안을 보내 30초 답장으로 하나의 여름 약속을
> 확정한다.

## 2. 해결할 문제

여름에 만나고 싶은 사람은 있지만 약속을 먼저 꺼낼 때 세 가지
마찰이 생긴다.

1. `언제 볼까?`처럼 열린 질문은 상대에게 결정 부담을 넘긴다.
2. 날짜·활동·준비 역할을 한꺼번에 대화하면 결론이 늦어진다.
3. 일정 투표 도구는 실용적이지만 한 사람에게 말을 거는 감정과
   계절감을 살리지 못한다.

이 제품은 장소를 추천하거나 예약하는 서비스가 아니다. 보내는
사람이 두 개의 구체적인 선택지와 가능한 날짜를 먼저 좁히고, 받는
사람이 하나를 선택함으로써 약속을 닫는 데 집중한다.

## 3. 대상과 사용 상황

### 핵심 대상

- 친구, 가족, 연인, 동료 중 실제 연락 가능한 한 사람
- 여름에 만나고 싶지만 먼저 구체적인 제안을 꺼내기 어려운 사람
- 별도 가입이나 긴 입력 없이 모바일에서 바로 답하고 싶은 사람

### 대표 상황

- `이번 주말에 만나자`고 말만 하고 날짜를 정하지 못했다.
- 휴가 전 한 번 보고 싶지만 무엇을 할지 정하기 번거롭다.
- 상대에게 모든 결정을 맡기지 않고 내가 먼저 작은 역할을 맡고 싶다.

### 비대상

- 세 명 이상의 집단 합의: 별도 제품 `모여름`의 범위다.
- 장소 검색·예약·결제까지 한 번에 하려는 사용자
- 관계 유형, 궁합, 성향 진단을 원하는 사용자

## 4. 경험 목표

### 목표 감정

`망설임 → 기대 → 선택받음 → 약속이 잡힌 안도감`

### 세션 목표

| 역할 | 목표 시간 | 세션 종료 상태 |
| --- | ---: | --- |
| 보내는 사람 | 중앙값 60초 이하 | 답장 대기 링크 공유 |
| 받는 사람 | 중앙값 30초 이하 | 여름 약속 확정 |
| 다시 온 사람 | 10초 이하 | 최신 약속 상태 확인 |

### 첫 10초 약속

- 직접 진입: `누구에게 어떤 두 여름을 건넬지` 바로 고를 수 있다.
- 초대 진입: 보낸 사람의 두 선택지와 가능한 날짜를 먼저 본다.
- 재진입: 홈 설명보다 답장 대기 또는 확정 상태를 먼저 본다.

## 5. 핵심 제품 원칙

1. **선택에는 실제 차이가 있다.** 배경색만 다른 장식 선택을 두지
   않는다.
2. **보낸 사람과 받는 사람의 화면은 다르다.** 같은 입력 폼을
   반복시키지 않는다.
3. **상대의 답이 공유 상태를 바꾼다.** 원본 링크에서도 최신 상태가
   보여야 한다.
4. **결과는 약속이다.** 날짜, 장면, 두 사람의 역할이 모두 있어야
   `확정`이라 부른다.
5. **부담을 강요하지 않는다.** 거절 점수나 읽음 압박을 만들지 않고
   링크 만료와 새 제안 경로를 제공한다.
6. **재방문을 속이지 않는다.** 의미 없는 출석이나 잠금 해제로
   지표를 만들지 않는다.
7. **플랫폼 기능은 핵심 흐름에만 쓴다.** 공유·식별·상태 복원·분석이
   없으면 제품 약속이 성립하지 않는다.

## 6. 핵심 흐름

### 6.1 직접 진입 — 두 개의 여름 고르기

첫 화면에서 서비스 설명을 길게 하지 않고 여름 장면 카드 여섯 개를
보여준다. 보내는 사람은 서로 다른 두 장면을 고른다.

초기 장면 세트:

1. 바다나 물가 보러 가기
2. 노을 산책하기
3. 여름밤 야시장 가기
4. 시원한 실내 나들이
5. 빙수나 아이스크림 먹기
6. 늦은 저녁 동네 피크닉

카드에는 장면 이름과 예상 시간대만 표시한다. 장소명, 정확한 위치,
가격 추천은 하지 않는다.

규칙:

- 정확히 두 개를 선택해야 한다.
- 선택 순서는 우열이나 추천 순위가 아니다.
- 선택은 공유 전까지 자유롭게 바꿀 수 있다.

### 6.2 가능한 날짜와 내가 맡을 일

보내는 사람은 가능한 날짜를 2~3개 고르고, 각 날짜에 시간대 하나를
붙인다.

- 낮
- 노을 무렵
- 저녁

날짜 범위:

- 오늘 이후 날짜만 가능
- 최대 30일 이내
- 같은 날짜 중복 불가

이어서 자신이 먼저 맡을 일을 하나 고른다.

- 장소 후보 찾기
- 이동 방법 알아보기
- 간식 준비하기
- 준비물 챙기기

짧은 말 한마디는 선택 사항이다.

- `이번 여름은 내가 먼저 말 걸게.`
- `둘 중 하나, 같이 해볼래?`
- `거창하지 않아도 한 장면 남기자.`
- 직접 입력 20자

표시 이름은 8자 이내 선택 입력이며 비워두면 `여름 친구`로 쓴다.

### 6.3 미리보기와 토스하기

공유 전 화면에서 다음을 한 번에 확인한다.

- 두 장면
- 가능한 날짜와 시간대
- 내가 맡을 일
- 표시 이름과 한마디

`이 두 장면 토스하기`를 누르면 서버에 초대를 만들고, 받는 사람용
딥링크를 생성한다. 공이 화면을 가로지르는 0.5초 이하 자동 전환은
장식이며 누르는 시점이나 속도를 기록하지 않는다.

공유가 취소되더라도 생성한 초대는 `답장 대기`에서 다시 공유할 수
있다. 공유 시도 자체를 성공으로 간주하지 않는다.

### 6.4 초대 진입 — 어느 여름을 받을래?

받는 사람은 별도 인트로 없이 다음 순서로 본다.

1. `OO님이 두 개의 여름을 토스했어요.`
2. 보낸 사람의 한마디와 맡은 일
3. 두 장면 카드
4. 가능한 날짜

받는 사람은:

- 장면 하나
- 날짜와 시간대 하나
- 자신이 맡을 일 하나

를 고른다.

받는 사람의 역할:

- 사진 남기기
- 길 찾기
- 음악 고르기
- 현장 분위기 맡기

선택 응답:

- `좋아, 이 장면으로 가자.`
- `이 날짜라면 좋아.`
- `이번에는 내가 이어갈게.`
- 직접 입력 20자

표시 이름은 8자 이내 선택 입력이다. 제출 전 선택을 자유롭게
수정할 수 있으며 `이 약속 받기`를 누른 뒤에는 첫 유효 응답으로
확정한다.

### 6.5 확정 공개 — 우리의 여름 약속

확정 결과는 세 컷 웹툰으로 구성한다.

1. **토스 컷:** 보내는 사람과 두 개의 제안
2. **리시브 컷:** 받는 사람이 선택한 장면과 답장
3. **약속 컷:** 날짜, 시간대, 두 사람의 역할과
   `우리의 2026 여름 약속` 스탬프

필수 표시:

- 두 표시 이름
- 선택된 장면
- 확정 날짜와 시간대
- 각자 맡은 일
- 두 사람이 입력한 문장

주요 CTA:

- 보내는 사람: `답장 확인하기` 또는 `약속 다시 보기`
- 받는 사람: `내가 다른 사람에게 토스하기`
- 공통: `약속 한 컷 공유하기`

새 토스는 기존 초대에 사람을 붙이는 릴레이가 아니라 독립된 새
초대다.

### 6.6 답장 대기와 재진입

보내는 사람이 앱을 다시 열면 익명 사용자 키를 기준으로 자신의
최근 초대를 불러온다.

- 답장 대기
- 약속 확정
- 기간 만료

답장 대기 화면에는 상대의 접속·읽음 여부를 표시하지 않는다.
재촉 문구 대신 `링크 다시 보내기`와 `새 제안 만들기`만 제공한다.

확정 화면은 약속 날짜까지 다시 볼 수 있고, 지난 날짜에는
`지나간 약속`으로 중립 표시한다. 실제 만남 여부를 자동으로
단정하지 않는다.

## 7. 상태 모델

### Invite 상태

| 상태 | 의미 | 가능한 행동 |
| --- | --- | --- |
| `draft` | 공유 전 로컬 편집 | 수정·삭제·생성 |
| `pending` | 서버 생성, 응답 대기 | 다시 공유·조회 |
| `confirmed` | 첫 유효 응답으로 확정 | 결과 조회·공유 |
| `expired` | 생성 후 30일 또는 모든 날짜 경과 | 조회·새 토스 |
| `cancelled` | 보내는 사람이 무효화 | 조회·새 토스 |

상태 전이는 서버에서 한 번만 처리한다.

`draft → pending → confirmed`

`pending → expired | cancelled`

확정된 초대는 응답자가 다시 열어도 동일한 결과를 보여준다. 두 번째
응답 시도는 저장하지 않고 이미 확정됐음을 알린다.

### 실패 처리

- 초대 생성 실패: 입력을 기기에 보존하고 재시도
- 공유 취소: `pending` 초대에서 다시 공유
- 잘못되거나 만료된 링크: 오류 코드 대신 새 토스 CTA
- 응답 중 네트워크 실패: 선택을 보존하고 중복 제출 방지
- 익명 키 조회 실패: 초대 응답은 허용하되 내 초대 목록은 제한
- 서버 지연: 2초 후 진행 상태와 재시도 안내

## 8. 재미 가설

| 가설 | 기대 감정·행동 | 검증 신호 |
| --- | --- | --- |
| 두 선택지의 긴장 | 상대가 무엇을 고를지 궁금함 | 전송 후 예상 선택을 말함 |
| 비대칭 역할 | 받는 화면이 답장처럼 느껴짐 | 같은 설문 반복이라는 반응 없음 |
| 결과 변환 | 답이 장식이 아니라 약속을 바꾼다고 느낌 | 날짜·역할을 결과에서 회상 |
| 웹툰 공개 | 확정 순간을 저장·공유하고 싶음 | 결과 공유·캡처 의향 |
| 작은 선제 약속 | 상대에게 부담을 덜 줌 | `먼저 맡아줘서 편하다` 반응 |

재미는 아직 사용자 증거가 없는 가설이다. 인터랙티브 프로토타입과
실제 전송 테스트 전에는 재미를 승인하지 않는다.

## 9. 시각·상호작용 방향

시각 방향은 `여름 스포츠 웹툰 × 로맨틱 코미디 × 실제 약속 카드`다.

### 보존

- 동일한 두 캐릭터
- 한낮·노을·여름밤 계절 색감
- 말풍선과 만화 컷 구획
- 공을 건네는 짧은 장면 전환

### 변경

- 비치볼 도형은 금지 표시처럼 보이지 않도록 패널 분할을 재설계
- 첫 화면은 긴 폼이 아니라 큰 장면 카드 두 개 선택에 집중
- 받는 화면은 스파이크가 아니라 선택을 받아내는 리시브 장면
- 최종 포스터는 인원 수 대신 확정 날짜와 역할을 중심으로 구성

### 금지

- 속도선과 충돌 이펙트로 판정·성공을 암시
- 반복 공 애니메이션
- 버튼을 누르는 시점을 기다리게 하는 연출
- 작은 화면에서 장면 카드보다 장식이 앞서는 구성

`prefers-reduced-motion`에서는 공 전환 없이 다음 컷으로 즉시 이동한다.
선택 상태는 색만이 아니라 테두리·체크·텍스트로 함께 표시한다.

## 10. Apps in Toss 활용

### P0

- 비게임 사용자 식별키로 내 초대 목록과 재진입 상태 복원
- `getTossShareLink`로 받는 사람의 초대 화면 딥링크 생성
- `share`로 초대와 확정 결과 공유
- 비게임 내비게이션 바와 뒤로가기
- 분석 이벤트와 핵심 전환 설정

### P1

- 답장 도착 또는 약속 임박 알림
- 알림 동의는 사용자가 구체적인 알림을 요청하는 순간에만 받음
- 확정 카드용 동적 OG 이미지

알림 승인이나 동적 OG가 없어도 P0 핵심 흐름은 작동해야 한다.

## 11. 비게임 경계

### 허용

- 두 장면 중 하나를 사람이 직접 선택
- 날짜와 역할을 합쳐 사실 기반 결과 표시
- 답장 대기·확정·만료 상태 표시
- 각 사용자가 만든 독립 초대 수를 개인 기록으로 조회

### 금지

### 개발 진입 게이트

1. 보내는 사람과 받는 사람의 화면이 다른 프로토타입이 있다.
2. 두 기기에서 원본 초대 상태가 `pending → confirmed`로 바뀐다.
3. 다섯 쌍 테스트에서 실제 전송 4건 이상, 응답 3건 이상이다.
4. 세 쌍 이상이 `카톡보다 제안을 정리하기 편했다` 또는 동등한
   실제 가치를 설명한다.

### 중단 조건

- 실제 전송이 5건 중 3건 미만
- 응답 완료가 5건 중 3건 미만
- 다수가 결과를 `예쁜 카드`로만 설명하고 날짜·역할을 회상하지 못함
- 다수가 `카톡으로 하는 것과 차이가 없다`고 평가
- 2026-07-27 12:00 KST까지 두 기기 상태 전이가 작동하지 않음

중단 조건을 넘기면 아이콘·썸네일·추가 이미지를 만들지 않고,
